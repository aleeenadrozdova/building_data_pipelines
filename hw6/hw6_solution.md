# HW6 — Кейсы, где DataFrame (и Spark SQL) быстрее RDD

Дополняет hw4 (там RDD выигрывал на «грязных» данных). Здесь — обратные кейсы на регулярных
аналитических данных e-commerce. См. `RUN_ME.md`, скрипты `gen_data.py`, `cases_df_vs_rdd.py`,
`sql_vs_df.py`.

## 3 кейса: DataFrame > RDD (что даёт Catalyst/Tungsten)

### C1. Множественные агрегации — `groupBy().agg(sum, avg, min, max, count)`
- **DF:** Catalyst строит **один `HashAggregate`** с несколькими выражениями агрегации,
  Tungsten генерирует векторизованный код (whole-stage codegen) — данные не
  сериализуются в промежуточные типы, всё числовое.
- **RDD:** ту же логику приходится писать руками в `reduceByKey` (seq/comb), каждая запись
  — Python-объект с pickle-сериализацией.
- **Выигрыш:** один проход без сериализации + codegen.

### C2. Оконные функции — топ-N в группе (`row_number` over window)
- **DF:** Catalyst выполняет окно одним `Window`-узлом, сортировка внутри партиции,
  `row_number` считается на месте, без ручной группировки повторно.
- **RDD:** приходится делать глобальную сортировку + `groupByKey` + ручной `take(N)` —
  больше пересылок и локальных коллекций.
- **Выигрыш:** window pushdown и оптимизированный план против ручных сортировок.

### C3. Вложенные типы — `array<struct>`, `explode` + агрегация
- **DF:** Tungsten работает с нативными вложенными типами (без сериализации), `explode`
  — оптимизированная операция, раскрытие + агрегация одним планом.
- **RDD:** вложенную структуру приходится вручную разбирать в Python-объекты и обходить —
  медленно, много кода, риск ошибок по вложенности.
- **Выигрыш:** нативная работа с complex types вместо ручного парсинга.

## (*) 2 кейса: SQL быстрее DataFrame API

### S1. Одно GROUP BY со многими агрегатами vs несколько `groupBy().agg()` + join
- **SQL:** `... GROUP BY user_id` с 5 агрегатами — Catalyst строит **один `HashAggregate`**,
  один `Exchange` (shuffle) и один проход.
- **DF API (наивный):** если агрегаты разбить на несколько `groupBy().agg()` и соединить
  через `.join()`, Spark сделает **несколько `Exchange`** — лишние shuffle.
- **План:** в SQL меньше `Exchange`-узлов → быстрее. (Правильный DF-подход — один `agg()`
  со всеми агрегатами, тогда DF тоже один проход; но «эквивалентный» наивный DF-код —
  классическая ловушка, где SQL выигрывает.)

### S2. Несколько оконных функций в одном SELECT vs отдельные `.over()`
- **SQL:** оконные функции в одном `SELECT` Catalyst умещает в один проход с одной пересылкой.
- **DF API:** «наивная» цепочка из трёх `.withColumn(..., over(w))` запишется в один проход,
  если оконные спецификации идентичны (см. фактический прогон: они сливаются даже у DF).
- **Когда реально проигрывает DF:** разные `PARTITION BY`/`ORDER BY` (разные спецификации
  → разные сортировки/пересылки) или окна, построенные от разных чтений.
- **План:** число `Window`/`Exchange`-узлов смотрите в `explain("extended")` — см. замеры ниже,
  где это проверено фактически (в т.ч. неожиданное слияние окон у DF на Spark 4.x).

## Замеры (полный прогон: `data`, 5M строк, min из 3 повторов)

*Реальные цифры, получены прогоном в local-режиме на полном датасете (5M строк). Сводки —
в `cases_df_vs_rdd_RESULTS.txt` и `sql_vs_df_RESULTS.txt`. Для сравнения: на контрольном
`data_small` (200k) выигрыш был гораздо скромнее (×1.1–×1.8) — на малых данных всё
умещается в JVM/pickle-стоимость скрыта.*

### C1–C3 (DF vs RDD), сек, data=5M строк

| Кейс | DataFrame | RDD | Кто быстрее |
|---|---|---|---|
| C1 много-агрегации | 0.665 | 12.455 | DF (**×18.7**) |
| C2 оконная топ-N | 1.481 | 15.988 | DF (**×10.8**) |
| C3 вложенные типы | 0.545 | 10.854 | DF (**×19.9**) |

На полном датасете разрыв на **порядок**: RDD каждый раз сериализует записи в Python-объекты
(pickle) и гоняет их через Py4J, а DF/Tungsten работает нативно с типизированными данными.
Максимальный выигрыш — у вложенных типов (C3): ручной парсинг `array<struct>` в Python
оказался в ~20 раз дороже нативного `explode`.

### S1–S2 (SQL vs DF API) + сколько `Exchange`/`Window`-узлов в планах

| Кейс | SQL, сек | DF API, сек | Узлов: SQL / DF |
|---|---|---|---|
| S1 GROUP BY | 0.622 | 0.700 | Exchange: **1 / 3** |
| S2 окна | 0.122 | 0.140 | Exchange: 1 / 1, Window: 2 / 2 |

- **S1 — подтверждено:** SQL `GROUP BY` с 5 агрегатами = **1 `Exchange`**, «наивный» DF
  (два `groupBy().agg()` + join) = **3 `Exchange`** (по одному на каждый groupBy + join) —
  отсюда выигрыш SQL. Правильный DF-вариант — один `agg()` со всеми агрегатами, тогда у DF
  тоже 1 `Exchange`.
- **S2 — неожиданный результат (важно):** SQL и DF **одинаковы** (0.151 vs 0.149) и оба дают
  **1 `Exchange` + 2 `Window`** в плане. Причина: у обоих оконные спецификации идентичны
  (`PARTITION BY user_id`), и Catalyst **сливает (fuse) окна с одинаковым partition spec
  в один проход независимо от API**. Ожидание «три `Window`-узла у DF» не подтвердилось на
  Spark 4.x для одной и той же lineage. Реальный проигрыш DF появился бы, если бы окна имели
  разные `PARTITION BY`/`ORDER BY` (разные спецификации — разные сортировки/пересылки) или
  строились от отдельных чтений.
- Значения узлов сняты из `explain("extended")` / `executedPlan` того же контрольного прогона.

## Вывод: когда какой API выбирать

| Контекст | Выбор |
|---|---|
| Аналитика по регулярным данным, агрегации, окна, nested-типы | **DataFrame / Spark SQL** (Catalyst + Tungsten) |
| Гибкая логика, обработка «грязных»/нерегулярных данных, контроли на партициях/памяти | **RDD** (hw4) |
| Много связанных агрегатов / несколько окон в одном запросе | **SQL** — объединяйте в одно выражение, а не цепочку `.over()`; хинты/планы смотреть через `explain` |
| Смешанный пайплайн (bronze→silver→gold) | bronze на этапах гибкости — RDD; по мере нормализации — DF/SQL |
