# HW4 — Задача, где RDD доказывает преимущества над DataFrame

**Вступление (джун говорит «буду всё писать на DataFrame»):** как архитектор я показываю,
что есть класс **реалистичных** задач, где RDD объективно лучше по четырём осям: компактность
кода, скорость, надёжность, гибкость. Ниже — сама задача и разбор по каждой оси.

---

## 1. Выбор задачи

> **Обработка «грязных» сырых событий с нерегулярной схемой.**
> На вход — поток событий из брокера записей в «сыром» слое озера данных (бронзовый слой).
> Данные приходят в текстовом/JSON-представлении и обладают четырьмя свойствами, которые
> и делают задачу проблемной для типовых табличных API:
>
> 1. **Схема нерегулярна** — у разных типов событий (просмотр / корзина / покупка / возврат)
>    совершенно разный вложенный состав полей; часть полей отсутствует.
> 2. **Есть мусор** — часть записей вообще не парсится (невалидный формат), их нельзя
>    «выбросить молча»: за ними может быть ценная или аудируемая информация.
> 3. **Есть дубликаты** — одно и то же событие записано дважды; нужно чистить по ключевым
>    полям, не затрагивая соседних.
> 4. **Данных много и они «шумные»** — важно контролировать память при промежуточной обработке
>    и не «раздувать» shuffle.


---

## 2.тГибкость

**Проблема типового табличного API (DataFrame):**
DataFrame требует **единой, жёстко типизированной схемы**. Чтобы прочитать разнотипные события,
приходится либо:
- строить «широкую» схему со всеми возможными полями всех типов (и тогда почти каждая строка —
  куча пустых ячеек), либо
- явно объявлять схему **для каждого типа события отдельно** и потом как-то собирать их вместе.

Любое добавление нового типа события = правка объявления схемы. Работа с **разной глубиной
вложенности** (у одних событий вложение одно, у других — другое) тоже превращается в громоздкие
выражения «разверни-склей».

**Что даёт RDD:**
RDD оперирует объектами общего вида (ключ → значение, например разобранный словарь событий).
Ветвление по типу события — это **обычная управляющая логика** («если тип такой — беру эти поля,
если другой — эти»). Новая разновидность события добавляется простым расширением условия,
никаких изменений «схемы» в коде нет. Работа с разной глубиной вложенности — обычный доступ к
вложенным структурам.

**Вывод:** для данных, которые **принципиально структурно разнородны**, табличный API
заставляет «подгонять» данные под единую схему; RDD работает с данными такими, какие они есть.

---

## 3. Компактность кода

Табличный API заставляет выражать «если/иначе» и «достань из разной вложенности» набором
декларативных выражений с массой вспомогательных конструкций: условные значения, распаковка
вложенных структур, обработка пустых значений, разворот коллекций. Одна скромная нормализация
строки на DataFrame выглядит как набор громоздких выражений.

На RDD та же логика записывается **обычной функцией преобразования одной записи** — ветвление,
цикл по элементам коллекции, пропуск отсутствующих полей. Кода заметно меньше, он читается как
понятный алгоритм, а не как «цепочка трансформаций».

**Вывод:** на нерегулярных и вложенных данных RDD-решение компактнее — меньше кода,
легче читать, меньше мест для ошибок.

---

## 4. Скорость 

Казалось бы, оптимизированный движок табличного API должен быть быстрее любых «ручных» RDD.
Но в этой задаче выигрыш даёт **ручной контроль**, которого у DataFrame нет:

1. **Дубликаты можно удалить без обмена данными.** В RDD дубликаты убираются **внутри каждой
   партиции** локальным набором виденных ключей — никакого перемешивания (без shuffle).
   В табличном API операция «убери дубликаты» — это глобальная операция равенства, которая по
   определению требует перераспределения строк между партиями (shuffle).
2. **Контроль разбиения.** RDD читается и обрабатывается с нужным числом партий; порядок
   операций и «где что считается» — под нашим контролем. В табличном API планирование
   «физического» исполнения решает движок, и повлиять на него менее явно.
3. **Переиспользование промежуточного результата.** Промежуточный слой можно намеренно
   зафиксировать (держать в памяти/на диске), чтобы не пересчитывать парсинг несколько раз.
   В табличном API кэширование тоже есть, но решение «что кэшировать» зависит от оптимизатора.

На «грязных» данных дубликатов много, а тратить shuffle на их удаление — значит тратить самое
дорогое (перемещение данных между партиями). Ручной контроль позволяет этого **не делать**,
поэтому RDD-решение быстрее на данной задаче.

**Вывод:** ручные оптимизации RDD (дедупликация без shuffle, контроль партий,
прицельное переиспользование) дают выигрыш в скорости именно там, где табличный API «платит»
за генерализацию.

---

## 5. Надёжность (Reliable: возможность управлять памятью и полнотой)

1. **Память.** Грязные данные бывают настолько «шумными», что нельзя держать в памяти всё
   (все ключи, все ошибки). RDD позволяет **явно ограничить потребление** на партию: держать
   только ограниченный набор рабочих ключей и вытеснять лишнее, а промежуточные данные при
   переполнении **сбрасывать на диск** (а не падать «из памяти»). Такой уровень управления
   в табличном API недоступен напрямую — движок сам решает, что держать, и может упасть/вытеснить
   «неочевидно».
2. **Полнота (не терять ничего).** При разборе строк часть из них валидна, часть — нет.
   RDD позволяет **разделить потоки** (валидные данные и «карантин») и **сохранить битые строки
   отдельно** для разбора — ничего не теряется, есть аудируемый след. В табличном API битые
   строки обычно молча не попадают в результат, и «история» о них пропадает.
3. **Предсказуемость поведения.** Ручное управление означает, что поведение «что где живёт»
   предсказуемо и воспроизводимо — важно на проде, где «неожиданное падение по памяти» дорого.

**Вывод:** на задачах с «мусором» и большими объёмами RDD надёжнее: ограничиваешь память
сам, а битые данные не теряешь (карантин + сброс на диск вместо падения).

---

## 6. Границы (когда RDD — не козырь)

Эти четыре оси сильны **только на нерегулярных/«грязных» данных**. Как только данные
«устаканились» в регулярном, типизированном слое и начинаются массовые **агрегации, оконные
функции, работа с вложенными (но уже регулярными) структурами** — там прямой оптимизатор
(Catalyst/Tungsten, векторизованное исполнение, продвинутые физические планы) обгоняет RDD.
Поэтому ответ не «RDD лучше», а **«разные инструменты под разные стадии пайплайна»**:
- «сырой» нерегулярный слой, контроль памяти/партий, карантин мусора → **RDD**;
- регулярный аналитический слой, агрегации, витрины → **DataFrame / SQL**.

---

## 7. Итоговый ответ джуниору

> Твоё «всё на DataFrame» справедливо для регулярных данных и аналитики. Но есть класс
> реалистичных задач — сырые, структурно разнородные, «грязные» данные в начале пайплайна, —
> где RDD сильнее: код компактнее (обычное ветвление, а не объявление схем), быстрее
> (дубликаты убираем без shuffle, партии и память под контролем), надёжнее (битые строки
> уходят в карантин, а не теряются; память ограничиваем сами). Правильный подход — использовать
> RDD именно там, где он силён (бронзовый/сырой слой), и переключаться на DataFrame/SQL на
> регулярных слоях (серебро/золото). Тогда мы берём лучшее от обоих.
