# HW5 — Оптимизация Spark-приложений (RetailFlow)

**Датасет:** заказы e-commerce (~20 млн строк) + маленький справочник каталога (100 строк).
Сгенерированы с **реалистичными проблемами**: перекос ключей (3 горячих продавца дают ~65%
заказов), множество мелких файлов/партиций, маленькая справочная таблица для join.
См. `RUN_ME.md` (код: `gen_data.py`, `optimize_join.py`, `optimize_agg.py`, `opt_upsert.py`).

---

## 1. Выявленные проблемы (что мешает эффективной обработке)

| # | Проблема | Симптом |
|---|---|---|
| P1 | Join большой таблицы с маленьким справочником без broadcast | лишний shuffle всех данных (sort-merge join) |
| P2 | Data skew при `groupBy(seller_id)` (горячие продавцы) | одна-две партиции-«раковины», время = самая нагруженная партиция |
| P3 | Много мелких партиций/файлов после `partitionBy` | избыточные мелкие задачи, накладные расходы планировщика |
| **P4*** | **Инкрементальные обновления витрины: полное переписывание ради 1–5% изменений** | каждая «правка» = перезапись всей таблицы (стоимость/время на I/O и shuffle) |

## 2. Оптимизации и ожидаемый эффект

### P1 → broadcast join
Маленький справочник (порог по умолчанию 10 МБ) шлём на все исполнители хинтом
`F.broadcast(catalog)` — join идёт без shuffle. AQE/`autoBroadcastJoinThreshold` могут решить
это автоматически.
**Ожидание:** заметно быстрее, чем sort-merge (особенно на большом orders).

### P2 → salting горячего ключа
Добавляем к `seller_id` случайный суффикс `0..9` (`_salt`), агрегируем по
`(seller_id, salt)`, затем схлопываем. Горячий ключ «расплёскивается» на ~10 партиций.
**Ожидание:** сильно быстрее наивного groupBy на перекошенных данных.

### P3 → контроль числа партиций перед записью / чтением
`repartition`/`coalesce` перед записью, уменьшение `spark.sql.shuffle.partitions`, чтение
с нужным числом партиций — меньше мелких файлов и задач.

### P4* (свободный кейс, не из классического списка) → двухслойный merge-on-read
Классика: чтобы обновить 1–5% строк витрины (например, ежедневное изменение цены/остатка в
RetailFlow), пайплайн переписывает **всю таблицу** (full rewrite). Решение — **два слоя**:
- **базовый слой** — стабильная партиция, переписывается редко;
- **слой изменений** — пишем **только изменённые строки** (дешёвая маленькая запись);
- **чтение** — `base JOIN updates` + `coalesce(price)`: маленький join, почти без накладных;
- **компакция** — периодически сливаем объединённое в новый базовый слой (без частых full rewrite).

**Ожидание:** при доле изменений 1–5% полное переписывание в разы/на порядки дороже, чем
запись слоя изменений; overhead чтения при merge-on-read мал. Выгода тем сильнее, чем меньше
процент изменившихся строк относительно объёма витрины.

## 3. Замеры (сек, min из N повторов)

*Замеры выполнены на контрольном датасете: 300к заказов (upsert — 200к), local-режим.*

### P1–P3 (`optimize_join_RESULTS.txt` / `optimize_agg_RESULTS.txt`)
| Операция | Наивный | Оптимизация | Комментарий |
|---|---|---|---|
| Join (P1) | 0.747 | broadcast: **0.318** | broadcast в ~2.3 раза быстрее; AQE (0.384) тоже помогает |
| Agg groupBy seller (P2) | 1.075 | salted: 1.128 | на 300к salting не выигрывает (оверхед второго прохода > выигрыш на маленьких данных) |
| — AQE (вкл.) | — | 0.778 | на малых данных AQE/coalesce лучше наивного и salted |

### P4 (merge-on-read) — `opt_upsert_RESULTS.txt` (200к строк)
| Доля обновления | Full rewrite (сек) | Запись слоя изменений (сек) | Merge-read (сек) |
|---|---|---|---|
| 1% | 1.214 | 0.294 | 0.507 |
| 5% | 0.499 | 0.232 | 0.287 |
| 20% | 0.466 | 0.240 | 0.244 |

**Интерпретация P4:** на малой таблице full rewrite «дёшев» сам по себе (всё в памяти/кэше),
поэтому выигрыш modest; экономия strongly растёт с увеличением размера витрины и падением доли
изменений (при фиксированной доле 1% на таблице в десятки ГБ full rewrite стоит минуты, а слой
изменений — секунды).

## 4. Выводы (по фактическому контрольному прогону)

- **Broadcast vs sort-merge:** подтверждено — маленький справочник выгодно раздавать в broadcast
  (2.3× на тесте); AQE тоже снимает лишний shuffle автоматически.
- **Salting:** на малом датасете не даёт выигрыша (дополнительный ширящийся проход дороже, чем
  сам перекос на 300к) — salting оправдан на **больших** перекошенных данных, где одна партиция
  реально «тянет» стадию (это важный честный вывод: не все оптимизации универсальны).
- **AQE:** стабильно помогает (0.78 против 1.08 у наивной агрегации) — включать по умолчанию.
- **Merge-on-read (P4*, свободный кейс):** модель «база + слой изменений + компакция» дешевле
  полного переписывания, тем больше выгода, чем меньше доля изменений и больше витрина;
  классические табличные форматы (hw7) делают это из коробки.
- **Практика для RetailFlow:** включать AQE; для большого перекоса — salting только на ключах,
  где он реально нужен; для часто обновляемых витрин закладывать слой изменений (или перейти на
  Delta/Iceberg — см. hw7).
