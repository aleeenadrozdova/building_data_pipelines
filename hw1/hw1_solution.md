# HW1 — Архитектура аналитической платформы RetailFlow (e-commerce)

Тема проекта: аналитическая платформа интернет-магазина/маркетплейса **RetailFlow**.
Ниже — ответы по 8 блокам архитектурного решения.

---

## 1. Источники данных

**Какие источники?**

| Источник | Данные | Тип |
|---|---|---|
| Мобильное приложение | События: `view`, `cart.add`, `cart.remove`, `purchase`, `navigation`, `search`, `promo_shown` | Поток событий |
| Веб-сервер (nginx/backend) | Access-логи, сервисные логи | Логи |
| Транзакционная БД (PostgreSQL/MySQL) | Заказы, платежи, доставка, продавцы, каталог, цены/остатки | OLTP (CDC) |
| Внешние API | Статусы доставки, данные служб доставки, маркетинговые кампании | API |

**Формат на выходе из источника**

- Мобильное/веб-приложение: **JSON** (события отправляются на HTTP API шлюза, сериализуются в Avro при записи в Kafka).
- Веб-логи: plain text / JSON-lines (nginx access log).
- OLTP БД: структурные строки, вычитываются через **CDC (Debezium, формат Debezium JSON/Avro)** или периодические выгрузки (Parquet из replica).
- Внешние API: JSON (REST), отдаваемый поставщиком.

**Объём**

- События клиента: пик ~**40–50K событий/сек**, в среднем ~10K событий/сек. Итого ~**800–900 млн событий/день → ~0.5–1 ТБ/день** в сжатом виде (Avro/Parquet).
- Веб-логи: ~150 ГБ/день в сыром виде.
- CDC из OLTP: изменения ~50–100 млн записей/день, ~200 ГБ/день.
- Оценка: **суммарный intake ~1.5–2 ТБ/день**, хранение растущее.

**Критичность**

- **Свежесть:** события клика/корзины важны для real-time-аналитики (рекомендации, антифрод) — свежесть минуты. Потери недопустимы для `purchase`/`payment` (финансовые и бизнес-метрики) — эти события идут в **используемые/точно-один-раз** каналы.
- **Допустимая потеря:** вспомогательные маркетинговые события (`promo_shown`) — допустима небольшая потеря (at-least-once + дедупликация по `event_id`).
- Заказы/платежи — **критичные**, ни в коем случае не теряем (это источник выручки и аудита).

---

## 2. Сбор и интеграция данных

**Как данные поступают в систему**

- Мобильное/веб → HTTP **API-шлюз** (Kong/ALB) → **Kafka** (единая шина событий, `events.*` топики).
- CDC: **Debezium** читает WAL OLTP и пишет в Kafka (`cdc.*`).
- Веб-логи: **Fluent Bit/Vector** собирают с узлов и пишут в Kafka или напрямую в озеро.
- Внешние API: периодические **poll-джобы** (Argo Workflow → Spark/скрипт), реже webhook → Kafka.

**Надёжность приёма**

- Kafka — буфер/брокер с репликацией (`replication.factor=3`, `acks=all`), гарантированное хранение.
- DLQ (dead-letter queue) — события, не прошедшие десериализацию/валидацию, складываются в отдельные топики `dlq.*` для ручного разбора.
- Ретраи и идемпотентность: у каждого события уникальный `event_id`, приёма с дедупликацией.
- Мониторинг lag'ов и ошибок продюсеров.

**Разные форматы источников**

- Единая **схема в Schema Registry (Confluent/Redpanda)** — Avro/Protobuf.
- На входе события нормализуются в общий канонический формат: `event_id`, `event_type`, `ts`, `user_id`, `session_id`, `payload`.
- Формат-специфичная трансформация вынесена в отдельный слой ingestion (сервис нормализации), чтобы аналитика работала с единой моделью.

---

## 3. Хранилища и озёра данных

**Неизменённые исходные данные (Raw)**

- **Озеро данных на объектном хранилище (S3/MinIO)** в формате **Parquet/Avro**, табличном формате **Apache Iceberg** (слой **bronze**).
- Iceberg даёт: версионирование (time travel), ACID-коммиты, snapshot'ы, партиционирование.

**Обработанные структурированные данные**

- Слои:
  - **bronze** — сырые данные как есть (immutable).
  - **silver** — очищенные, дедуплицированные, обогащённые, схема выверена (Delta/Parquet).
  - **gold** — витрины/агрегаты для потребителей (реализованы в StarRocks/витринах для BI).
- Горячие данные запросов — в **StarRocks/ClickHouse** (или Trino поверх Iceberg) для интерактивной аналитики.

---

## 4. Обработка и трансформация

Основные трансформации (Spark, batch по событийным топикам + stream по горячим):

- **Очистка** — отбраковка пустых/битых событий, нормализация типов, приведение времени к UTC.
- **Дедупликация** — по `(event_id)`/`(user_id, ts, event_type)` для идемпотентности.
- **Обогащение** — join с каталогом, ценами, продавцом, гео по IP, признаками кампаний.
- **Сессионизация** — склейка событий в сессии пользователя (окно неактивности >30 мин).
- **Агрегация** — витрины продаж по категориям/продавцам/часам, funnel покупок, LTV, retention.
- **Проверки качества** встроены в этапы (см. блок 6).

---

## 5. Каталоги данных и метаданные

- **Data Catalog:** единый каталог (напр. **DataHub/Amundsen/Unity Catalog**) — где потребитель ищет таблицы/витрины.
- **Schema Registry** хранит схемы (Avro/Protobuf) и версии.
- **Метаданные таблиц**: сервис каталога/Iceberg metastore + тех. метаданные (владелец, SLA, частота обновления, источник).
- **Происхождение данных (lineage):** фиксируется на уровнях:
  - **job-level** — какие джобы из каких топиков/таблиц читали и писали (собирается из Airflow/Argo + Spark listener'ов);
  - **field-level** — отслеживание, из какой колонки какого источника пришло значение (пропагируется из трансформаций).
- Ручная маркировка бизнес-глоссария и владельцев данных.

---

## 6. Качество и управление данными

- **Проверки качества** (data quality tests, напр. **Great Expectations / Soda**):
  - полнота (не NULL, не пустые),
  - целостность (FK на каталог, корректные id),
  - уникальность (дедупликация, правильные PK),
  - диапазоны/распределения (метрики не упали вне допустимого коридора),
  - свежесть (данные за ожидаемые окна появились).
- **Когда и как запускаются:** как отдельные этапы в пайплайне — после `silver`-слоя и перед публикацией витрин; также **тестовые проверки** на синтетических данных в CI.
- **Что делать при провале:**
  - fail-fast: пайплайн останавливается, витрина не публикуется (или публикуется предыдущая валидная версия — Iceberg time travel / backfill);
  - алерт команде владельцу (PagerDuty/Telegram) с деталями,
  - DLQ/карантин для битых данных,
  - разбор первопричины и фикс, повторный запуск (backfill).

---

## 7. Безопасность и управление доступом

- **Аутентификация:** SSO/OIDC для людей (Okta/Keycloak), mTLS/SPIFFE‑SPIRE для сервис-сервисов, тайные креды сервисов — через **HashiCorp Vault** (детально в HW10).
- **Авторизация:** 
  - **Ranger/Unity Catalog** для таблиц зеро (row/column-level security),
  - роли: аналитик (читает silver/gold), ML-инженер (читает bronze/silver), DBA/DE (полный доступ), BI-конечный пользователь (только gold). 
- **Разграничение доступа к слоям:** bronze — только DE/ML, silver — аналитика, gold — BI/витрины. Личные данные (PII: e-mail, телефон) — псевдонимизация/маскирование, данные клиента — строгий доступ, соответствие 152-ФЗ/GDPR.
- Шифрование: at-rest (на объектном хранилище), in-transit (TLS).

---

## 8. Оркестрация и автоматизация

- **Кто запускает пайплайн:** **Airflow** (текущий курс: Argo Workflows — см. HW11/12) оркестрирует batch-джобы.
- **Расписание и зависимости:** DAG'и с часовой/суточной периодичностью; зависимости upstream/downstream; backfill и catchup.
- **Контроль версий задачи:** 
  - код джоб версионируется в git (SemVer), образ собирается в registry (тег = версия);
  - DAG/Workflow-файлы хранятся в git и деплоятся через CI/CD (GitOps, Argo CD);
  - перезапуск конкретной версии/бекфилл по тегу.
- Авторетраи с экспоненциальной задержкой, алерты на сбои (см. HW13).

## Итоговая схема (текстовая)

```
 Мобайл/Веб ──HTTP──▶ API-шлюз ──┐
 nginx-логи ──Fluent Bit─────────┼──▶ Kafka (events.* / cdc.* / dlq.*)
 OLTP БД ──Debezium(CDC)────────┘        │
 Внешние API ──poll-workflow─────────────┤
                                          ▼
                                   [ Schema Registry ]
                                          ▼
                       ┌───────── Spark ingest (bronze: Iceberg/Parquet) ─────────┐
                       │             transform (silver: clean/dedup/enrich)        │
                       └─────────────────────────┬─────────────────────────────────┘
                                                 ▼
                                            gold-витрины
                                                 ▼
                              StarRocks / Trino ◀── BI (Grafana/Superset)
                                              │
                              Каталог + метаданные + lineage (DataHub)
                              Качество данных (Soda/GE) + DLQ
                              Оркестрация (Airflow/Argo) + CI/CD (GitOps)
                              Безопасность (SSO/mTLS + Vault + Ranger)
                              Мониторинг (Prometheus + Grafana)
```
