# HW9 — Сравнительный анализ распределённых SQL-движков: Trino vs StarRocks

Контекст RetailFlow: интерактивная аналитика/BI поверх витрин (gold) и больших таблиц озера.

---

## 1. Классификация и контекст

- **Trino (бывш. PrestoSQL)** — MPP-движок **запросов (query engine)**, не хранилище.
  Данные не хранит: читает из объектного хранилища/озера (Hive/Iceberg/Delta), Postgres, Kafka
  и т.д. Массивные параллельные запросы, ANSI SQL, федеративные запросы.
- **StarRocks** — MPP **СУБД/хранилище с собственной моделью хранения** (таблицы, индексы,
  zone maps, материализованные представления), изначально OLAP-направленность (происходит
  от Doris), очень быстрые точечные и агрегирующие запросы, поддержка `UPDATE`/`DELETE`,
  real-time ingestion из Kafka/CDC.

**Ключевое отличие сразу:** Trino — «перебираем данные извне», StarRocks — «держим данные у себя
в материализованном виде». Отсюда разница и в производительности, и в применении.

---

## 2. Бенчмарки

### Ссылки на авторитетные источники

- **StarRocks official benchmark** (docs.starrocks.io / блоги «StarRocks vs Trino/Presto»):
  заявляют ускорение агрегаций и join'ов в разы против Trino на TPC-H/TPC-DS в hot-cache сценарии.
  *Комментарий к оценке:* это «домашние» бенчи производителя; сравнение идёт на их условиях
  (данные уже лежат и прогреты у StarRocks, у Trino — внешний холодный Parquet).
  Переносить 1:1 на наши условия нельзя.
- **trino.io benchmarks / community-сравнения** (техноблоги, коммьюнити-тесты TPC-DS через
  TPC-DS kit): Trino на «своих» данных (озеро) силён на широких сканах и федеративных
  запросах; худшие латентности объясняются отсутствием кэша/индексов — это плата за чтение
  внешних форматов «как есть».
- **Осторожность при сравнении:** TPC-H/TPC-DS изначально нагружают «горячее» хранилище,
  поэтому адекватное сравнение движков должно оговаривать размещение данных (холодное озеро
  vs загруженные таблицы), иначе цифры недобросовестны.


| Запрос | Ожидание по источникам |
|---|---|
| Full scan по Parquet (озеро) | быстрее Trino: читает напрямую; StarRocks сначала грузит в свои таблицы |
| Фильтр + агрегация (hot) | быстрее StarRocks: индексы/zone maps + данные уже у себя |
| Join большой×малая (broadcast) | сопоставимо; зависит от раскладки и статистики |
| Топ-N по категории | быстрее StarRocks на прогретых данных |
| Cold read из озера | быстрее Trino: нет этапа копирования/приёма данных |

**Вывод по бенчам:** результат сильно зависит от размещения данных. На
«горячем» собственном хранилище StarRocks почти всегда быстрее по агрегациям и точечным
запросам; на холодном озере и федеративных/разнородных источниках сильнее Trino.

## 3. Ключевые различия

| Аспект | Trino | StarRocks |
|---|---|---|
| Роль | query engine (псевдо-stateless) | OLAP-СУБД с хранилищем |
| Хранение | внешнее (S3/Iceberg/Delta/PG/Kafka) | собственные таблицы (материализованные вью, индексы) |
| Ingestion | нет приёма данных (только чтение) | встроенный приём из Kafka/CDC/файлов, real-time |
| Обновления | read-only поверх источников | UPDATE/DELETE, primary-key-таблицы |
| Материализация | внешние таблицы / для предпросчёта — внешние | материализованные вью и таблицы внутри |
| Оптимизации | планирование (CBO), AQE, join-стратегии, pushdown в источники | zone maps, индексы, табличные ключи, колоночные форматы |
| Мульти-источник/федерация | сильная (адаптеры) | слабее (ориентирован на собственные данные) |
| Модель развёртывания | псевдо-stateless координатор + исполнители | coordinator + BE-узлы с данными (stateful) |
| SQL | расширенный ANSI | расширенный ANSI (без части федеративных фич) |

## 4. Анализ рисков внедрения

| Риск | Trino | StarRocks |
|---|---|---|
| **Задержка появления данных** | низкая — читаем что уже есть в озере | требует предварительного приёма данных в свои таблицы — задержка ingestion-процедур |
| **Операционная сложность** | ниже (stateless, легко масштабируем на выполнение) | выше (stateful, нужно управлять replica/backup/schema эволюцией) |
| **Хранение/управление данными** | нет (полностью зависит от озера) | нужно поддерживать отдельное хранилище + синхронизацию с озером |
| **Двойственность источников истины** | нет (источник = озеро) | возможно «два источника» (озеро + StarRocks) → reconciliation |
| **Зрелость/позиционирование** | очень зрелый, гигантское комьюнити | моложе для больших кластеров; часть фич уже на уровне (оконные функции и т.п.), но комьюнити меньше |
| **Обучение команды** | низкое (SQL + знакомство с федерацией) | среднее (модель хранения, партиционирование, индексы) |
| **Lock-in** | минимальный (читает открытые форматы) | средний (свое хранилище, открытый Apache-проект — приемлемо) |

## 5. Итоговое решение для RetailFlow

- **Основной движок интерактивной аналитики/BI — StarRocks** поверх пред-материализованных
  витрин (gold), куда данные доставляются через пайплайны (Ingest из Kafka/озера). Это даёт
  низкие латенции для dashboards и повторяющихся агрегаций в дневном BI.
- **Trino** оставляем как **единый фасад/федеративный слой** поверх озера (bronze/silver и
  ad-hoc/исследовательские запросы, join с внешними источниками, «что угодно по озеру»),
  где не нужна высокая латентность и нет смысла синхронизировать данные в StarRocks.

**Логика:** комбинируем достоинства — горячие, повторяемые витрины на StarRocks (скорость,
материализация), холодные/разношёрстные запросы и федерацию на Trino (гибкость, нейтральность к
озеру). Один поставщик данных (озеро) остаётся источником истины, StarRocks — скорее
проекционный/когортный кэш витрин, что снижает риск двойных источников (reconciliation
обеспечивается пайплайном, как и для любого хранилища витрин).
