# Задание для DE («КонсультантПлюс»): навыки Spark/Scala

Локальная Spark-задача (Scala + Maven) по данным пользовательских сессий системы
«КонсультантПлюс». Датасет: учебная модель сессий — один файл = одна сессия,
события: начало/конец сессии, быстрый поиск (`QS`), карточка поиска
(`CARD_SEARCH_START`), открытие документа (`DOC_OPEN`). Всего 10 000 сессий
за 2020 год (361 день), ~175 тыс. строк.

Цели работы (по заданию):
- разобрать формат событий самостоятельно (в т.ч. учесть, что формат менялся и
  записи местами битые);
- построить и запустить Spark-задачу на Scala;
- посчитать две метрики;
- опубликовать исходный код и результаты.

## Ход работы: что мы делаем и где

### 1. Изучили формат данных — `data/`, раздел «Формат данных» ниже
Файл = сессия, строка = событие. Выяснили эмпирически (и отразили в парсере):
- **ид. документа** — `БАЗА_НОМЕР`, где в базе могут быть цифры (`RLAW080_115230`),
  поэтому идентификатор распознаётся регуляркой, а не «по словарю баз»;
- **поздний формат** `DOC_OPEN` (в конце датасета) — **без даты** (6 566 строк из
  102 872): такие открытия парсим, но в разбивку «по дням» они не попадают;
- **id поисков уникальны в пределах сессии**: 10 id из 17 137 встречаются в двух
  сессиях — значит привязка открытия к поиску должна учитывать сессию;
- текст запросов/параметров в cp1251, для метрик не нужен → парсер работает с
  ASCII-префиксами и не зависит от кодировки текста;
- в логах есть мусор (дубли результата, оборванные строки) → парсер не падает,
  а копит предупреждения.

### 2. Модель события — `model/Event.scala`
Одно плоское представление всех трёх видов событий
(`kind` = `quick_search` / `card_search` / `doc_open`), чтобы события легко
превращались в Spark `Dataset[Event]`:

| Поле | Что хранит | Заполняется для |
|---|---|---|
| `kind` | вид события (константы в объекте `Event`) | все |
| `day` | дата события `YYYY-MM-DD` (пусто, если даты нет) | QS, Card, DocOpen |
| `searchId` | id поиска, к которому относится событие | QS, Card (результат), DocOpen |
| `params` | параметры карточки `id параметра → значение` | Card |
| `docs` | документы в результатах поиска | QS, Card |
| `doc` | открытый документ | DocOpen |
| `session` | идентификатор сессии (файла) — для корректной привязки открытий | все |

### 3. Парсер — `parser/SessionParser.scala`
`SessionParser.parse(содержимое, session)` за один проход по строкам превращает
файл в `Result(events, warnings)`:
- `QS` «съедает» следующую строку-результат (`<search_id> <док1> ...`) — она не
  становится отдельным событием;
- `CARD_SEARCH_START` собирает параметры `$<id> <значение>` до
  `CARD_SEARCH_END` и строки-результата;
- `DOC_OPEN` разбирает оба формата — с датой (4 токена) и без (3 токена, поздний
  формат); невалидный разбор не роняет задачу, а уходит в предупреждения;
- «висячие» строки-результаты (дубли) и неопознанные строки — в предупреждения.

### 4. Определения метрик — `metrics/Metrics.scala`
Чистые функции (без Spark) — **эталон**, на котором в тестах проверяем правила:
- `cardSearchesForDocument` — метрика 1 (см. ниже; `$0` = номер документа);
- `opensByDayForQuickSearchedDocuments` — метрика 2: открытие учитывается, только
  если документ был в результатах именно того быстрого поиска, на который
  ссылается `DOC_OPEN` (привязка по `(session, searchId, doc)`), и есть дата.

### 5. Spark-задача — `Main.scala`
Конвейер:
```
wholeTextFiles(data) ──parse──▶ (path, Result(events, warnings))
      │  диагностика: сессий, событий, предупреждений (+ примеры)
      ▼
events = события в Dataset[Event]
      │
      ├─ Метрика 1 (карточные поиски с $0 = ACC_45616)        → results/metric1.txt
      └─ Метрика 2 (джойн по (session,searchId,doc) + группировка по (day,doc))
                                                              → results/metric2/part-*.csv
```
Аргументы: `--input <каталог> --out <каталог>` (каталог читается через
`wholeTextFiles`, поэтому каждый файл — отдельная сессия). Плюсы/минусы подхода и
замеры — в самом коде комментариями.

### 6. Тесты — `SessionParserSpec.scala`
8 юнит-тестов без Spark: разбор сессии, карточки, битые строки, дубли форматов,
обе метрики, поздний формат, базы с цифрами, привязка открытий к сессии.
Запуск: `mvn test`.

### 7. Запуск — `run.sh` / раздел «Сборка и запуск»
`run.sh` собирает jar (если ещё нет) и зовёт `spark-submit`. Флаги
`spark.driver.host/bindAddress=127.0.0.1` добавлены намеренно: на этой машине
Spark не может привязаться к случайному порту из-за VPN (`BindException
error(-49)`), loopback это обходит.

## Формат данных

Файл = сессия. Строка = событие:

```
SESSION_START <dd.MM.yyyy_HH:mm:ss>
QS <dd.MM.yyyy_HH:mm:ss> {<текст запроса>}
<search_id> <док1> <док2> ...          # результат быстрого поиска
CARD_SEARCH_START <dd.MM.yyyy_HH:mm:ss>
$<id параметра> <значение>             # параметры карточки (по данным: $134 — текст, $0 — номер документа)
CARD_SEARCH_END
<search_id> <док1> <док2> ...          # результат карточного поиска
DOC_OPEN <dd.MM.yyyy_HH:mm:ss> <search_id> <док>
SESSION_END <dd.MM.yyyy_HH:mm:ss>

# поздний формат (в конце датасета): даты нет
DOC_OPEN <search_id> <док>
```

Наблюдения по данным:
- **id поиска** — число (иногда отрицательное), уникально в пределах сессии
  (10 id из 17 137 встречаются в двух сессиях); на него ссылается `DOC_OPEN`
  (открытие «привязано» к поиску).
- **ид. документа** — `БАЗА_НОМЕР` (например `ACC_45616`, `LAW_221940`,
  `PBI_253397`; в базе могут быть цифры: `RLAW080_115230`, `REXP140_38180`).
- Текст запросов/значения параметров — в кодировке cp1251; для метрик не нужен
  (структурные префиксы ASCII), поэтому парсер не зависит от кодировки текста.
- В логах встречаются: строки без привязки к поиску (дубли результата), отсутствие
  результата у поиска, «оборванные»/мусорные строки. Парсер считает их
  предупреждениями и не роняет задачу.

## Метрики

**Метрика 1 — «Количество раз, когда в карточке производили поиск документа
с идентификатором ACC_45616».**
Определение: карточный поиск, у которого параметр-«номер документа» (`$0`)
равен `ACC_45616`. Таких поисков в данных — **24**.
Замечание: ряд карточных поисков лишь *возвращал* `ACC_45616` в результатах
(это другой сценарий: поиск по тексту), они не учитываются. Для полноты их
также можно посчитать отдельным запросом.

**Метрика 2 — «Количество открытий каждого документа, найденного через быстрый
поиск, за каждый день».**
Определение: `DOC_OPEN` несёт `search_id` — поиск, из которого открыт документ.
Документ считается «найденным через быстрый поиск», если он был в результатах
именно этого быстрого поиска (привязка по тройке `session, search_id, документ`).
id поисков уникальны в пределах сессии (10 id встречаются в двух сессиях) — поэтому
джойн идёт с учётом сессии. Для таких открытий считаем количество по дням
(день = дата открытия). Результат — таблица `(день, документ, количество)`.
Открытия позднего формата (без даты, их ~6,6 тыс.) в разбивке «по дням» не участвуют.
Контрольные значения на данных: ~222 877 документов найдено через быстрый поиск;
~82 362 открытия этих документов; ~70 807 уникальных пар (день, документ).

## Требования

- Java 17, Maven 3.8+.
- Apache Spark 4.2.0 (локально), Scala 2.13 (входит в сборку через spark).
  `mvn` сам скачает spark-sql со склад (первый раз — долго).

> О сборке: `spark-sql` и `scala-library` указаны как `provided` — это даёт
> тонкий jar (без повторно скачанных Spark-классов). При запуске через
> `spark-submit` нужные библиотеки уже есть в кластере Spark, поэтому jar
> маленький. Внутри кода Spark-классы доступны: на время сборки Maven их
> скачивает, на время запуска — берёт из установленного Spark.

## Сборка и запуск

```bash
# 1) собрать тонкий jar (тесты прогнать заодно):
mvn clean package

# 2) запустить Spark-задачу (данные лежат в ./data — распакованный архив):
./run.sh
# или явно:
./run.sh <каталог с файлами сессий> <каталог результатов>
```

Эквивалент вручную:
```bash
spark-submit --class ru.consultantplus.de.Main --master local[*] \
  --conf spark.driver.host=127.0.0.1 \
  --conf spark.driver.bindAddress=127.0.0.1 \
  target/de-task-1.0.0.jar --input data --out results
```

Запуск из IntelliJ IDEA Community Edition: «Open» → выбрать `pom.xml`, Maven
подтянет зависимости; запустить `ru.consultantplus.de.Main` с аргументами
`--input data --out results` (или через `spark-submit`).

Тесты (парсер и метрики) без Spark:
```bash
mvn test
```
