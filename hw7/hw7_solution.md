# HW7 — Табличные форматы: Delta, Hudi, Iceberg

Эксперименты и сравнение на фактовых данных e-commerce (RetailFlow). Код и запуск — в `scripts/`, `RUN_ME.md`.

---

## 1. Проблемы одновременной записи и как их решает каждый формат

| Проблема | Delta Lake | Hudi | Iceberg |
|---|---|---|---|
| Потеря / затирание при параллельных записях | **Optimistic concurrency**: при коммите проверяется версия таблицы; при расхождении — `ConcurrentWriteException`, воркер **повторяет коммит** автоматически | **MVCC + timeline**: новые коммиты добавляются в timeline; конфликт разрешается optimistic-подходом, при наличии lock-provider (ZooKeeper/файл) жёстче | **Snapshot isolation**: каждый коммит — новый snapshot через compare-and-swap на метаданных; конфликт -> повторная попытка коммита |
| Дубликаты данных | нет — single writer-семантика через log | дедуп по key (upsert через `primaryKey`+`preCombineField`) | append-only / копировать-on-write; дубли управляются потребителем |
| Перекрывающиеся аппенды из двух джоб | сериализация коммитов (ретрай) | optimistic + (опционально) lock-provider | compare-and-swap + линейная история |
| Гонка на метаданных | JSON-лог, CAS | timeline-файлы | метаданные таблицы (manifest) с атомарным обновлением |

**Эксперимент** (`concurrent.py`, по одному прогону на формат): два воркера пишут в одну
таблицу пересекающиеся ключи с `version=1`. На установленном Spark 4.2.0 эксперимент не
завершён: Hudi и Iceberg несовместимы с этой версией Spark (см. §2), поэтому честных замеров
конкурентной записи нет.

## 3. Кейс: когда Hudi или Delta Lake оправданы вместо Iceberg

Сравниваем по ключевым особенностям:

| Фактор | Iceberg | Delta Lake | Hudi |
|---|---|---|---|
| Возраст/зрелость | нейтральный формат, широкий стек (Flink/Spark/Trino/Presto) | сильная привязка к Spark/Databricks | strong upserts/инкрементальная обработка, хорош для стриминга и частых on-column updates |
| Бенчмарк-ниша | **большие аналитические чтения, много движков, ACID + time travel** | эксплуатит Spark/ML, простой API | **частые точечные апдейты/апсерты, CDC, дедуп на больших объёмах** |
| Конкуренция | snapshot isolation | optimistic concurrency | MVCC + timeline |

**Когда выбрать Hudi/Delta вместо Iceberg:**

- **Hudi** — если нужны **массовые точечные обновления/апсерты** (частое обновление строк,
  CDC, «залатать» десятки тыс. строк ежедневно) и **инкрементальная загрузка** изменений
  (incremental reads). Iceberg тоже поддерживает copy-on-write/merge-on-read, но Hudi здесь
  исторически сильнее и проще в стриминговых сценариях.
  *Пример RetainFlow:* контур отмены/возврата заказов, где ежедневно правится подмножество
  строк заказа без полноценного перезалива витрины.

- **Delta Lake** — если команда **на Spark/Databricks**, нужен простой ACID + time travel +
  `MERGE`/`OPTIMIZE` из коробки, и нет требований к много-движковому чтению.
  *Пример:* золотой слой витрин, где весь стек уже Spark и важна простота `MERGE`-обновлений
  и `OPTIMIZE` для компакции.

- **Iceberg** оставить как основной «озерный» формат для **аналитических gold/bronze**,
  когда важны нейтральность (несколько движков), дешёвые большие чтения и снимки.
