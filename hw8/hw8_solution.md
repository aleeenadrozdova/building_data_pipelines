# HW8 — Kafka-пайплайн событий RetailFlow (e-commerce)

Адаптация задания (в оригинале — Консультант Плюс по документам) под тему e-commerce:
разбиваем потоки событий маркетплейса на топики, проектируем партиции/ключи, политики хранения,
гарантии доставки и consumer-группы. В конце — схема и описание.

---

## 1. Топики (что разбиваем, партиции, ключи)

Все топики используют **Avro** и **Schema Registry** (имена подпартиций сокращены).

| Топик | Содержимое | Партиции | Ключ сообщения | Зачем такой ключ |
|---|---|---|---|---|
| `events.view` | просмотры товара | 24 | `(user_id, product_id)` | упорядоченность просмотров одного юзера по товару; равномерная раскладка |
| `events.cart` | добавление/удаление из корзины | 24 | `user_id` | все события одного юзера в одну партицию → консистентный порядок корзины |
| `events.purchase` | факты оплаты/заказов | 64 | `order_id` | заказ — атомарная единица; все его события в одном ключе → точечная обработка |
| `events.refund` | возвраты/отмены | 32 | `order_id` | связать с покупкой (join по порядку) |
| `events.delivery` | статусы доставки | 16 | `order_id` | связь по заказу |
| `cdc.orders` | CDC из OLTP (Debezium) | 32 | `order_id` (PK) | порядок изменения строки заказа |
| `cdc.sellers` | CDC продавцов/каталога | 8 | `seller_id` | редкие изменения — мало партиций |
| `dlq.events` | не прошедшие валидацию/десериализацию | 8 | — | карантин для ручного разбора |
| `metrics.agg` | готовые агрегаты (уже посчитанные витрины) | 16 | `metric_key` | потребители-витрины читают готовое |

**Почему именно столько партиций:** мощность — под целевой intake (пик ~50K/s событий клиента);
каждая consumer-группа получает ≤ партиций канала параллельно, а плановый объём больших групп
(дедуп/сессионизация) требует запаса партиций. Мелкие справочные топики (cdc.sellers) намеренно
мало партиционированы — меньше накладных, редкие апдейты.

## 2. Политики хранения (retention)

| Топик | Политика | Обоснование |
|---|---|---|
| `events.view` | **compact / короткий retention** (например, 24 ч или compact по ключу, если нужен последний просмотр) | просмотры важны для краткосрочной аналитики и рекомендаций; озеро уже хранит сыроё |
| `events.cart` | compact или короткий retention (24 ч) | актуальна только текущая корзина |
| `events.purchase` / `refund` / `delivery` | **относительно длинный retention (например, 7–30 дней) + backup в озеро** | финансовые/бизнес-данные — нельзя терять; из топика переливается в bronze |
| `cdc.orders` | **compact** (нужно последнее состояние строки + текущий log-префикс) | CDC: после обработки интересно последнее состояние; compaction удаляет старые версии «за лагом» |
| `cdc.sellers` | compact | каталог — только последнее состояние |
| `dlq.events` | длинный retention + алерт | битые данные разбирают вручную, спешить нельзя |
| `metrics.agg` | по необходимости (например, 48 ч) | готовые метрики — промежуточный буфер |

Тема: глобально — баланс «свежесть/стоимость хранения»: консервируем то, что нельзя перечитать
из озера; для всего, что уже перелито в bronze, retention может быть коротким.

## 3. Гарантии доставки

- **Продюсеры:** `acks=all` (синхронная устойчивость), `enable.idempotence=true` →
  exactly-once на уровне продюсера (нет дублей «из коробки» от переотправок).
- **Потребители:** приём через официальный консьюмер с commit-aми после обработки.
  Для **финансовых событий (`purchase`, `refund`, `cdc.orders`)** — **at-least-once + дедупликация
  по `event_id`/`order_id` на стороне обработки** (или транзакционный консьюмер для strictly-once).
- **Транзакционные продюсеры** (`transactional.id`) для end-to-end exactly-once, где нужна
  атомарность записи нескольких топиков (например, `purchase` + `metrics`).
- Kafka Cluster с `replication.factor=3`, `min.insync.replicas=2` — защита от потерь при сбое брокера.
- Схемы в Schema Registry (backward/forward compatibility) — десериализация не ломается про прод.

**Итог:** «финансовый контур» — строгие гарантии (EO + дедуп/транзакции), «маркетинговый/просмотры» —
at-least-once допустимо.

## 4. Consumer-группы (потребители)

| Группа | Что читает | Назначение |
|---|---|---|
| `group.ingest-view` | `events.view/*`, `events.cart`, ... | сервис нормализации -> в озеро (bronze) |
| `group.ingest-fin` | `events.purchase`, `cdc.orders`, `events.refund/delivery` | строгая запись финансов/заказов в bronze |
| `group.session` | все `events.*` | сессионизация, фрод-скоринг |
| `group.reco` | `events.view`, `events.cart` | рекомендации/ранжирование (низкая задержка) |
| `group.metrics` | `events.purchase`, `cdc.orders` | агрегация -> `metrics.agg` |
| `group.dlq` | `dlq.events` | разбор битых данных |

Каждая группа **независимо** перематывается по своим партициям → несколько downstream-команд
читают один топик без взаимных помех. Число консьюмеров в группе ≤ партиций топика.

## 5. Схема

```
 Производители                                   Брокеры Kafka (replication.factor=3)
 ┌─────────────┐   events.view/cart   ┌──────────────────────────────────────┐
 │ мобильное app├────────────────────▶│ events.view(24) events.cart(24)       │
 ├─────────────┤   events.purchase    │ events.purchase(64) refund(32)        │
 │ веб          ├────────────────────▶│ events.delivery(16)  ──┬─────────────┐ │
 │ API-шлюз     │                     │                        │             │ │
 ├─────────────┤   cdc.orders         │                    SchemaRegistry    │ │
 │ OLTP БД      ├──Debezium─▶ cdc.orders(32) cdc.sellers(8)    (Avro)        │ │
 ├─────────────┤                     │  dlq.events(8)                        │ │
 │ доставка API ├───── events.delivery│  metrics.agg(16)                      │ │
 └─────────────┘                     └───────────────────────────────────────┘
                                               │
                    ┌──────────────────────────┼───────────────────────────────┐
                    ▼                          ▼                                ▼
            group.ingest-*             group.session / group.metrics      group.reco
            (bronze: норм.)            (сессионизация/агрегаты)          (рекомендации)
                    │                          │                                │
                    ▼                          ▼                                ▼
               Озеро данных                 metrics.agg                    ранжирование
               (Iceberg)                  (витрины/BI)
```

**Описание к схеме:** события идут от клиентских сервисов через API-шлюз (чтобы не подключать
каждый сервис напрямую к брокерам) в топики `events.*`. CDC из OLTP — в `cdc.*`. Консьюмеры
разбиты на независимые группы: ingestion пишет в озеро, аналитика/рекомендации читают те же
топики для своих задач. Битые данные не теряются (DLQ). Готовые метрики агрегируются в
`metrics.agg` для витрин.
