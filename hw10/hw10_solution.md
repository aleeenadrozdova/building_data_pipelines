# HW10 — Управление секретами в Kubernetes: сравнение инструментов

Контекст RetailFlow: в кластере работают долгоживущие микросервисы и batch-джобы Spark,
нужны секреты (креды БД/Kafka/MinIO, ключи registry, токены GitOps). Сравниваем 3+ инструмента.

---

## 1. Кандидаты и критерии

Инструменты:
- **A. Native Kubernetes Secrets** (+ интеграция с External Secrets Operator рассказана отдельно).
- **B. HashiCorp Vault** (+ agent injector).
- **C. Sealed Secrets (Bitnami)**.
- **D. External Secrets Operator (ESO) + AWS/Google Secret Manager / Vault back-end** — как «прокси».

**Критерии (что важно для реального проекта):**
1. Безопасность хранения (encryption at rest/in transit, RBAC, audit).
2. Удобство разработки (GitOps-friendly, DX, сколько кода/манифестов).
3. Ротация секретов (возможность и простота).
4. Аудит и следов происхождения.
5. Производительность/масштаб (число секретов, latency выдачи).
6. Интеграция с GitOps/CI-CD (Argo CD, GitLab CI).
7. Стоимость внедрения (инфраструктура, эксплуатация, лицензирование).

---

## 2. Сравнение по критериям

| Критерий | Native Secrets | Vault | Sealed Secrets | External Secrets Operator |
|---|---|---|---|---|
| Хранение / at-rest | etcd, шифрование настраивается (encryption-provider) | собственное хранилище (или HSM), шифрование по умолчанию | в etcd кластера, зашифровано закрытым ключом (SealedSecret) | зависит от back-end (K8s-секрет / внешний менеджер) |
| RBAC/делегирование | слабое (на уровне Namespace/ServiceAccount) | сильное (политики по путям, namespace) | слабое (как K8s-секрет) | K8s RBAC + внешние роли |
| Audit | ограниченный (через audit-лог K8s) | полноценный audit log (кто/что/когда) | нет отдельного аудита | аудит внешнего менеджера |
| Ротация | вручную (пересоздать секрет), автоматизации нет | встроенные механики/агент, легко автоматизировать | вручную (пересоздать манифест) | возможна через внешний менеджер + sync |
| GitOps-friendly | плохо (секреты лежат открытым текстом в кластере; в git не кладут) | среднее (если класть не в git, выкатывать через агента) | **хорошо** (в git — зашифрованные SealedSecret) | **хорошо** (в git — ссылки/плейсхолдеры) |
| Latency/масштаб | отлично (etcd) | средняя (внешняя выдача, агент-инъекция) | отлично | средняя (внешние вызовы при синке) |
| Стоимость внедрения | нулевая | высокая (сервер Vault, HA, unseal, обучение) | низкая (контроллер-оператор) | средняя (оператор + внешний менеджер) |
| Где обычно применяют | простая подача статических секретов рабочим подам | централизованное управление секретами, dynamic secrets, PKI, комформность/аудит | GitOps-первый, когда на первом месте шифрование в git | синк секретов из внешнего менеджера (AWS SM, GCP SM, Vault) |

## 3. Сильные и слабые стороны + сценарии

**A. Native Secrets**
- + бесплатно, нативно, широко понятно, низкая латентность.
- – открытый текст в манифестах кластера, нет шифрования по умолчанию в etcd, слабый audit,
  нет ротации/динамики, секреты легко утекают в репозиторий при неаккуратности.
- *Сценарий:* статические настройки типа `BACKEND_PASSWORD` для второстепенных сервисов,
  когда не требуются audit/ротация.

**B. HashiCorp Vault**
- + централизованное хранилище, шифрование, audit, динамические секреты и PKI, RBAC по путям,
  агент-инъекция секретов в контейнеры без раскрытия в env.
- – дороже по эксплуатации (HA-кластер, unseal, TLS), латентность выше, интеграция сложнее.
- *Сценарий:* критичные секреты (банки/финтех, клиентские данные), где нужны audit, динамика,
  ротация и соответствие стандартам. Для RetailFlow — Vault для самых критичных (креды БД/PKI).

**C. Sealed Secrets (Bitnami)**
- + GitOps-первый: в git лежит только **SealedSecret** (зашифрованный), контроллер расшифровывает
  в кластере закрытым ключом. Простая DX.
- – закрытый ключ — единая точка компрометации в кластере; нет динамики/ротации/аудита.
- *Сценарий:* командный GitOps, когда нужно хранить секреты в репозитории безопасно без
  внешней инфраструктуры секретов.

**D. External Secrets Operator**
- + декларативный sync из внешнего менеджера секретов (Vault/SM) в K8s-секреты; GitOps-friendly
  (в git — ссылки), централизованное управление, автоматическая синхронизация/ротация.
- – требует внешнего менеджера (не самостоятельный), какая-то задержка синка, доп. оператор.
- *Сценарий:* middle ground — источник истины секретов вовне (Vault/SM), а в кластере —
  простые K8s-секреты с автосинком. Частый выбор для микросервисов + GitOps.

---

## 4. Итоговая рекомендация для RetailFlow

- **Критичные, динамические, с аудитом** (креды БД/платёжных сервисов, ключи подписи):
  **HashiCorp Vault** (агент-инъекция, аудит, возможность динамики/PKI).
- **Массовые секреты для микросервисов** (соединения с Kafka/MinIO/второстепенные креды):
  **External Secrets Operator** с back-end на Vault (или облачном менеджере) — декларативно,
  GitOps-friendly, авто-ротация и синк.
- **Native Secrets** — только для статических, некритичных значений, либо как итоговая подача
  из ESO в K8s-секрет.
- **Sealed Secrets** — вариант для команд без Vault/внешней инфраструктуры, когда нужен GitOps
  и «зашифрованный секрет в git»; либо как простой fallback.

**Главный критерий** — безопасность хранения + audit (финансовые/клиентские данные
RetailFlow) — поэтому ядро — Vault; удобство разработки и GitOps закрывает ESO.
